The solution

What makes Saathi different

The build guide adds more and more ways for the patient to express themselves. Saathi goes the other way: each turn should take the patient as little as possible. It does this in five ways, and each one fits into code you already have.

Answers shaped to the question

Most of what a partner says is a question, and the type of question already limits the answer. Before ranking anything, Saathi sorts the partner's last utterance into one of three types:

  • Yes/no (“Dawai li?”, “Are you cold?”): show two huge cards, Haan / Nahi.
  • Choice (“Thanda ya normal?”, “tea or coffee”): pull out the options and use them as the cards.
  • Open (kya, kab, kahan, what, when): fall back to today's 3 ranked suggestions from the phrasebook.

Why it's easy: for yes/no and choice questions the patient picks from two options. Effort goes from “find the right message” to “choose left or right”.

“My yes”: one movement, chosen by the patient

The guide asks for 6 calibration gestures, and the repo asks for 2–3 recordings of every ISL letter. Saathi's setup asks for one thing. The patient picks the movement that's easiest for them and does it three times, and Saathi learns that person's threshold for it. That movement then confirms everything. A second, opposite movement for “next” is optional.

Every option below is already detected by frontend/js/vision.js through MediaPipe blendshapes and head pose, so this is a threshold per user, not a new model.

Why it's easy: a patient with ALS can't give a thumbs-up but can still raise their eyebrows. Saathi uses whatever movement still works for them.

Signs work on day one, then learn as you talk

Today the ISL classifier starts empty. Saathi seeds it from data/ISL_Dataset: an offline script runs MediaPipe Hands over each image and stores the 254-dimension two-hand feature vector as a seed sample in sign_samples.

Each time the patient confirms a message that involved a sign, that live sample is saved under the confirmed label. Once a letter has 3 of the user's own samples, its seed samples are dropped. Nobody has to run a training session.

Before seeding: remove the 16 duplicate images, including the 8 that sit in both O and Q. Expect some images to fail hand detection at 128×128. H, J, Y and the digits aren't in the dataset, so they still need recording in the app.

The partner's phone becomes the second mic

A single laptop mic picks up both people, which is why the repo needs separate O and P keys. Instead, the partner scans a QR code and opens a /partner page on their own phone. That page has one big hold-to-talk button, which sends audio to the existing /api/partner. It also shows large captions of what the patient says, using /api/history.

Why it's easy: Saathi knows who is speaking from which device sent the audio, so the patient never presses a “partner is talking” key. A family member at home can use the same page.

Voice legacy, with spoken consent

For ALS and Parkinson's, the voice fades over time. Saathi asks for voice banking in week one, while the patient can still read the sample sentences. The recordings are stored but not cloned. When the patient is ready, they say the consent sentence aloud. Scribe checks it against the expected text, and only then can /api/voices/clone run. If there are no usable recordings, Voice Design builds a new voice from age, accent and warmth.

This meets the PS's “use only consented voices” rule with a step the patient performs, on top of the consent record the repo already keeps.

Risks

What could go wrong

  • Phone mic needs HTTPS. Browsers allow the mic only on a secure origin, so a plain LAN address won't work on the partner's phone. Serve over a tunnel or local HTTPS. Otherwise keep the phone for captions only.
  • Seed features must match live features. The Python seeding script has to reproduce the feature function in vision.js exactly. Add a parity test on one image before seeding.
  • The dataset has few signers and synthetic backgrounds. Treat seed accuracy as a rough starting point. Learn-on-confirm is what makes it personal.
  • Question detection in Hinglish is rule-based at first. If it guesses wrong, the open-question suggestions are still on screen, so a wrong guess costs one extra action and never blocks a reply.
  • Live behaviour is still untested. MediaPipe thresholds and the ElevenLabs endpoints haven't been run on a real machine with a key yet (repo README). Do that first.
Every simulated or acted number keeps a SIMULATED label in file names, database rows and the UI, as the PS and the build guide both require.
